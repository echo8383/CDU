## Historical code evidence

The decisive code change is commit `f2bf6b3c672b5de9eb5b684c142574e3602bfb76`
(`fix norm`, 2024-11-06). It changed `POLY.__init__` from no normalization
argument to `normalize=True` and added:

```python
if self.normalize:
    X = (X - X.min()) / (X.max() - X.min())
```

The parent implementation (`f2bf6b3^`) has no such transformation. The
official HP at the parent-era post-October-2024 history is still
`{'periodicity': 1, 'power': 4}`; the much earlier initial commit used power 2.
The historical `find_length_rank` behavior is separately restored by the
compatibility helper and yields window 264 for this sequence.

Relevant history audit: `POLY.py` changed at `23d609e` (initial implementation)
and `f2bf6b3` (`fix norm`); `HP_list.py` changed at `27150f8`, `37010a6`, and
`f2bf6b3` (post-October history uses POLY power 4); runner history includes
`b8d8e879` and `467a2eb`; the leaderboard table was merged at `887a360`.
None of these checked-out artifacts contains a POLY-141 score cache or runner
log.

## Controlled reconstruction

Using the current POLY class with `normalize=False` is behaviorally identical
to the parent implementation for this code path. With raw input, power 4,
window 264, and the official VUS implementation it gives
`0.9275813823665443` (absolute difference `3.33e-16`). With current
`normalize=True` it gives `0.699803801586029` (difference `0.227777580781`).
The score is deterministic under seed 2024; two normalized runs produced the
same hash. Window 100 does not repair the result.

## Root cause

**A — historical detector implementation mismatch, with merged-table provenance.**
The official table contains scores from the pre-`f2bf6b3` POLY behavior
(no input min-max normalization), while the current checkout applies min-max
normalization inside `POLY.fit`. The current runner and dataset path are not
the source of this particular discrepancy.
